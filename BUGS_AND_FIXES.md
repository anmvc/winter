# Winter 2.1.3 — Bug hunt and fixes

This document lists every bug found while reviewing `core` and `paper`, the reason it happened and how it was
fixed. The fixes are grouped by area; each entry names the files that were touched.

Everything was reviewed against the upstream repository (`thewinterframework/winter`): the fixes below are the
ones that were independently confirmed by later upstream commits (`421d39b` "add life cycle method to
decorator handler graph", `933a27b` "expose annotation", `ef23de5` "force OnReloadDecorator instance creation",
`3fe6eeb` "graph iterator now respects order", `f89e4aa` "primary handler", `8e69614` "use plugin class loader")
or by the behaviour documented in `readme.md`. Where upstream never fixed the
problem (several of the issues below are still present in 2.3.0) the reasoning is written down so the fix can be
reviewed on its own merits.

---

## 1. Annotation processing

### 1.1 `@ModuleComponent` was never processed
* **Files:** `module/processor/ModuleComponentAnnotationProcessor.java`
* **Cause:** the processor was not annotated with `@AutoService(WinterAnnotationProcessor.class)`, so it was never
  registered in `META-INF/services` and `WinterProcessor` never loaded it. `PluginComponentModule` was therefore
  never wired and `@ModuleComponent` classes were silently ignored.
* **Fix:** added `@AutoService` and made the `PluginModule` element lookup null-safe (`ProcessorUtils.asElement`
  returns `null` when the type is not on the classpath, which used to throw an NPE while processing).

### 1.2 Custom annotation types were lost as soon as one round generated sources
* **Files:** `processor/WinterProcessor.java`
* **Cause:** `loadHandlers()` was called once from `init()` and again from `getSupportedAnnotationTypes()`. The
  processor only iterates the annotations it *supports*, so a non-empty supported set is fine — but the second
  call created **new instances** of every stateful handler (`ClassWireProcessor` keeps the wired classes in a
  field), which were then discarded. On top of that, API projects left `handlers`/`handlersByAnnotation`
  `null`, and "`@WinterBootPlugin` annotation not found" was reported on **every** round instead of once.
* **Fix:** handlers are loaded once and memoized; API projects get empty (never `null`) collections; the missing
  plugin class is only reported on the last round (it may legitimately be generated by another processor).

### 1.3 Generated sources were not reproducible
* **Files:** `processor/WinterProcessor.java`, `processor/clazz/ClassWireProcessor.java`,
  `processor/context/ProcessorContext.java`
* **Cause:** `wiredClasses`, `ProcessorContext.requiredModules` and the per-annotation class list were
  `HashSet`s. `javac` does not order the elements of a round, so the generated `ProcessorModuleProvider` (and
  therefore the class list used at runtime) changed between builds.
* **Fix:** `LinkedHashSet` everywhere and a stable sort of the emitted class names.

### 1.4 Enums/records were skipped and generic components produced invalid code
* **Files:** `processor/clazz/ClassWireProcessor.java`
* **Cause:** `if (e.getKind() != ElementKind.CLASS) continue;` dropped enums and records, and
  `e.asType().toString()` returns `com.example.Foo<T>` for a generic type, so `com.example.Foo<T>.class` was
  written into the generated source — not a valid class literal.
* **Fix:** classes, enums and records are accepted (interfaces and annotation types are still skipped) and the
  canonical name is taken from `TypeElement#getQualifiedName()`.

### 1.5 `TemplateBuilder` aborted the whole compilation when a file already existed
* **Files:** `processor/template/TemplateBuilder.java`
* **Cause:** `Filer#createSourceFile` throws `FilerException` when the type was already created (by a previous
  round, or because the user wrote the class by hand). The exception was wrapped in a `RuntimeException`, which
  aborted the compilation with an error that mentioned neither the file nor the reason. The template was also
  rendered *inside* the `try`, so a rendering failure looked like an I/O failure.
* **Fix:** the template is rendered before the filer is touched, and a `FilerException` now emits a `NOTE` and
  keeps compiling.

### 1.6 `plugin.type` was locale sensitive and failed with a useless message
* **Files:** `utils/reflect/ProcessorUtils.java`
* **Cause:** `typeRaw.toUpperCase()` uses the default locale: on a Turkish JVM `"impl".toUpperCase()` is
  `"İMPL"` and `ProjectType.valueOf` throws. The exception (`No enum constant …`) did not mention the processor
  option, and leading/trailing spaces broke it as well.
* **Fix:** `trim()` + `toUpperCase(Locale.ROOT)` + an `IllegalArgumentException` naming the option and the
  accepted values.

### 1.7 `isChild` only looked at directly implemented interfaces
* **Files:** `utils/reflect/ProcessorUtils.java`
* **Cause:** the implementation cast the element to `TypeElement` (a `ClassCastException` for primitives/arrays)
  and only inspected `getInterfaces()` — a component extending a base class that implements `PluginModule` was
  rejected, and a transitive interface hierarchy was not followed either.
* **Fix:** the whole super type hierarchy (interfaces **and** superclasses, transitively) is collected, and
  non-declared types simply return `false`.

### 1.8 `@Expose` / API generation (rewritten)
* **Files:** `service/processor/ExposeAnnotationProcessor.java`,
  `service/processor/ExposeAnnotationProcessorAPI.java`,
  `resources/generated/ExposeInterfaceTemplate.java`
* **Causes and fixes:**
  1. `ExposeAnnotationProcessor` wired `ExposeAPIModule` **unconditionally**, even for plugins without a single
     `@Expose` type. The module class was never generated in that case, so the generated class list referenced a
     class that did not exist → `NoClassDefFoundError` at plugin startup. It is now only wired when the module is
     actually generated.
  2. The exposed class list was read from `META-INF/winter/exposed-classes.txt` on the `CLASS_PATH`. That file
     only exists when a separate API artifact is on the classpath; in a single project (`bypass.api`) it lives in
     the `CLASS_OUTPUT` and `openInputStream()` threw `FileNotFoundException`. The exception was caught and only
     reported, so the API module was wired **without** an implementation. Generation is now driven by the
     `<Plugin>API` interface itself (the source of truth), which works both for a generated and for a hand
     written interface, and does not depend on a resource on the classpath.
  3. The implementation was generated even when no `<Plugin>API` interface existed → unresolved symbol in the
     generated source. The processor now checks for the interface and does nothing when it is absent.
  4. `ExposeAnnotationProcessorAPI#getPluginPkg` called `element.getClass().getPackageName()`. `Element#getClass()`
     is `Object#getClass()`: it returns the **javac implementation class**
     (`com.sun.tools.javac.tree.JCTree$JCClassDecl`), so the API interface was generated into
     `com.sun.tools.javac.tree`. Fixed with `Elements#getPackageOf(element)`; a missing `@WinterBootPlugin` in
     `bypass.api` mode now produces an explicit error instead of an NPE.
  5. The interface was regenerated on every round that contained `@Expose` elements → `FilerException:
     Attempt to recreate a file` aborted the build. Generation is guarded (once per compilation) and the
     exposed-classes resource is written together with the interface.
  6. Elements were collected into a `HashSet`, so the generated interface (and its implementation) had a random
     method order; a `null` element (`getTypeElement` for a class that is not on the classpath) caused an NPE
     inside the `try` block. Elements are now sorted and a missing type is reported.
  7. `Default<Plugin>API` implemented the methods of the *class list* rather than the ones declared by the API
     interface, so a hand written API (or one with an extra method) produced a type that did not implement its
     interface. The methods — and their return types — now come from the interface.
  8. `@SupportedSourceVersion(RELEASE_17)` while the modules compile with Java 21 produced a warning on every
     compilation; it is now `RELEASE_21`.
  9. `ExposeInterfaceTemplate` used `Preconditions.checkNotNull/checkArgument` from **Guava**, which is only a
     `compileOnlyApi` dependency of this project: the generated `Provider` of a plugin that does not ship Guava
     failed with `NoClassDefFoundError` the first time the API was accessed, and a missing instance surfaced as
     an NPE instead of the documented `IllegalStateException`. It also did not end with a newline. The template
     now uses plain Java and throws the exceptions it documents.

## 2. Dependency graph

### 2.1 The topological order was inverted
* **Files:** `utils/graph/DfsGraph.java`
* **Cause:** `dfs` appends a node **after** visiting its dependencies (a correct post-order), and `ordered()`
  then called `Collections.reverse(order)`. Reversing a valid topological order produces the exact opposite:
  every node came **before** the nodes it depends on.
* **Impact:** `PluginModuleManager` loaded a module before its dependencies, and
  `LifeCycleDecoratorHandler` ran `@OnEnable(after = X)` methods before `X` (and `@OnDisable(before = X)` after
  it) — i.e. the documented ordering guarantees were exactly inverted.
* **Fix:** the post-order is returned as-is (`addAfter(after, before)` → `before` first,
  `addBefore(before, after)` → `before` first), the map/sets keep insertion order so the result is stable, and
  cycle detection reports the cycle it found.

## 3. Modules and components

### 3.1 `PluginModuleManager` could not survive a disable/enable cycle
* **Files:** `plugin/module/PluginModuleManager.java`
* **Causes and fixes:**
  * `registeredModules` was a `HashMap` (nondeterministic iteration); it is now `LinkedHashMap`, and
    `asGuiceModules()` returns a `LinkedHashSet` instead of `Set.copyOf` (which loses the order).
  * The injection and enable phases iterated the **graph**, not the modules that had actually completed the
    previous phase, so a module whose load failed was still injected/enabled, and enable ran a second time on
    modules that were already enabled. Both phases now iterate the recorded lists.
  * `alreadyLoaded` was never reset, and nothing recorded which modules were loaded/enabled, so after a disable
    the manager refused to load anything again. The state is tracked per module **class** and reset by
    `disableModules()`.
  * Modules were disabled in load order; they are now disabled in the reverse of the enable order, and a failed
    enable no longer leaves half-initialised modules behind (a partially enabled set falls back to the loaded
    one).
  * `disableModules()` aborted at the first failure and returned `false` for a manager that was never loaded;
    it now disables everything it can, reports the failure at the end and always releases the state.

### 3.2 `AbstractProcessorModule` disabled components that were never enabled
* **Files:** `wire/module/AbstractProcessorModule.java`
* **Cause:** `onDisable` iterated `activeComponents` (everything that passed the **load** conditions) and then
  cleared it. A component whose `ENABLE`-stage condition failed was still torn down, and after a disable the
  module had lost the list of components, so a re-enable did nothing.
* **Fix:** the enable phase records the components it actually started (`enabledComponents`) and only those are
  disabled; the lists are cleared at the beginning of a new load instead.

### 3.3 LOAD-stage conditions were ignored for `@ModuleComponent`
* **Files:** `module/PluginComponentModule.java`
* **Cause:** `depends()` returned every `@ModuleComponent` class, so a component annotated with
  `@RequiresPlugin(...)` (a `Stage.LOAD` condition) was registered, and its dependencies were loaded, even when
  the required plugin was missing.
* **Fix:** the classes are filtered with the same `LOAD`-stage evaluation the other modules use.

### 3.4 Providers were resolved from the first generic interface only
* **Files:** `provider/ProviderModule.java`
* **Cause:** `providerClass.getGenericInterfaces()[0]` fails (`ClassCastException` / `ArrayIndexOutOfBounds`)
  for a provider that extends a base class implementing `Provider<T>`, and only the first interface was
  considered. `configure()` also cleared `activeComponents`, so the enable/disable phases of the module lost
  every provider.
* **Fix:** the provided type is resolved with `TypeLiteral#getSupertype(Provider.class)` (works through the
  class hierarchy), unresolvable providers raise an actionable error, and the component list is preserved.

### 3.5 `@RequiresPlugin` never matched
* **Files:** `plugin/platform/PlatformPluginManager.java`, `paper/platform/PaperPlatform.java`,
  `wire/condition/common/plugin/RequiresPluginCondition.java`
* **Cause:** the condition runs in the **LOAD** stage, where Bukkit plugins are not enabled yet, but it used
  `PluginManager#isPluginEnabled` — which is `false` for every plugin at that point. The annotation therefore
  disabled the component even when the plugin was present.
* **Fix:** a new `isPluginPresent` (default: `isPluginEnabled`) is implemented by `PaperPlatform` with
  `getPlugin(name) != null`, and the condition uses it.

### 3.6 `@RequiresExpr` crashed on unexpected input
* **Files:** `wire/condition/common/expression/RequiresExpressionCondition.java`
* **Cause:** unchecked cast of the annotation, no `null` check on the resolver, and a blank expression was
  treated as `false`.
* **Fix:** defensive `instanceof`, `null`/blank handling and an explicit "only `true` passes" rule.

## 4. Services

### 4.1 Handlers created after a phase silently missed it
* **Files:** `service/ServiceManager.java`, `service/ReloadServiceManager.java`
* **Cause:** decorator handlers are created lazily, when a component using them is discovered. A handler created
  on demand (for instance `OnReloadDecoratorHandler` through `ReloadServiceManager#addOnReload`) never received
  `onPluginLoad`/`onPluginEnable`, and a handler that wanted Guice bindings was created *after* the injector had
  been configured, so its `onConfigure` was either never called or called too late.
* **Fix:** `ServiceManager` records the phases it already ran and replays them for a late handler. A handler that
  overrides `onConfigure` and is requested after the injection is configured now fails with an explicit message
  instead of silently dropping its bindings. `ReloadServiceManager` uses the new `getOrCreateHandler`, so
  `addOnReload(...)` no longer silently does nothing when no component is annotated with `@OnReload`.
* `handlers`/`registeredServices` are insertion ordered, the public API is synchronized (reloads come from other
  threads) and `services()` returns a copy instead of the internal mutable set.

### 4.2 `@Primary` bindings were nondeterministic
* **Files:** `service/decorator/injection/PrimaryHandler.java`
* **Cause:** `HashMap` + `put`, so two services annotated with `@Primary` for the same interface silently
  overrode each other in hash order, and only the **first** declared interface was bound. `binder.bind(X).to(X)`
  (an explicit `@Primary(MyService.class)`) is rejected by Guice with a cryptic error.
* **Fix:** insertion-ordered map, every declared interface is bound (not just the first), a conflicting
  `@Primary` declaration now fails with a message naming both services, and self-bindings are skipped.

### 4.3 Inherited and overridden methods were mishandled
* **Files:** `utils/reflect/Reflections.java`
* **Cause:** `findMethodsWith` only inspected `clazz.getDeclaredMethods()`, so a decorated method inherited from
  a base class was invisible, and the lookup used `clazz` as the "declaring class" (which fails for inherited
  methods).
* **Fix:** the whole class hierarchy is scanned, overrides are collapsed by name + parameter types (the most
  derived declaration wins, annotations are not inherited) and the method handle is looked up on the declaring
  class.

### 4.4 The `before`/`after` documentation said the opposite of what the code does
* **Files:** `service/meta/lifecycle/LifeCycleMethod.java`,
  `service/annotation/lifecycle/{OnEnable,OnDisable,OnReload}.java`
* **Cause:** `before()`/`after()` are the services the *annotated method* must run before/after, but the Javadoc
  described them as "the services that should be called before/after this method", and the annotations talked
  about an unrelated "priority" knob that does not exist. A method without `before`/`after` relations was also
  missing from the graph before `421d39b` (already part of 2.1.3), so the only remaining problem was the
  documentation — it is fixed, and graph ordering (section 2.1) is what makes the relations actually work.

## 5. Schedulers

### 5.1 Scheduled tasks were never cancelled
* **Files:** `service/decorator/scheduler/SchedulerDecoratorHandler.java`
* **Cause:** the handler ignored the task ids returned by the scheduler and had no `onPluginDisable`, so tasks
  kept running after a disable (and after a re-enable every task was scheduled a second time).
* **Fix:** every id is tracked and cancelled on disable; a second enable does not schedule anything twice; a
  failure while scheduling cancels what was already started.

### 5.2 A single `@ScheduledAt` was ignored
* **Files:** `service/annotation/scheduler/ScheduledAt.java`,
  `service/decorator/scheduler/SingleScheduledAtDecoratorHandler.java` (new)
* **Cause:** `@ScheduledAt` is `@Repeatable`. Java only wraps the annotation in `@ScheduledAtContainer` when it
  is repeated, so a method with exactly one `@ScheduledAt` was never seen by the container handler — and the
  annotation itself had no `@ServiceDecorator`, so nothing happened at all.
* **Fix:** `@ScheduledAt` is now a decorator for its own single-annotation handler, which builds the same
  `ScheduledAtMethod` with a one-element schedule list.

### 5.3 Time driven tasks used the wrong unit and could double fire
* **Files:** `service/annotation/scheduler/RepeatingTask.java`,
  `service/meta/scheduler/RepeatingTaskMethod.java`, `service/meta/scheduler/ScheduledAtMethod.java`
* **Causes and fixes:**
  * `RepeatingTask#unit` defaulted to `"MILLISECONDS"`, which is not a `TimeUnit` constant (the enum has
    `MILLIS`), so a task using the default unit failed to resolve.
  * `ScheduledAtMethod` polls at a fixed rate of one second and compared the *current* second. Because the poll
    period and the wall clock are not synchronised, two consecutive polls can land in the same second (the task
    runs twice) while another second is skipped entirely; after a lag spike the missed executions are lost. The
    hour was also resolved with a bare `requireNonNull` (an NPE without any context). It now walks every second
    between two polls, so each matching second fires exactly once and a missed poll is caught up.
  * `RepeatingTaskMethod` used `requireNonNull(...)` without a message (yielding a bare NPE) and happily
    scheduled negative delays/intervals.

## 6. Expressions and numbers

### 6.1 Converter lookup only matched exact types
* **Files:** `expression/converter/ConverterRegistry.java`, `expression/JexlExpressionResolver.java`
* **Cause:** the registry was a `Map<Source, Map<Target, Converter>>` lookup of the *runtime* class, so a
  converter registered for `Number` did not apply to `Integer`, and no converter applied to a subclass or to an
  interface. This is why `@RepeatingTask(unit = "SECONDS")` (a `String`) failed: only the enum constants
  registered in the JEXL context could be resolved.
* **Fix:** the exact type is tried first, then the class hierarchy, then the interfaces (transitively);
  `String → TimeUnit` and the common aliases (`MILLISECONDS`, `SECONDS`, … in any case) were added, and the
  number/string converters were completed.

### 6.2 The JEXL context was not thread safe
* **Files:** `expression/JexlExpressionResolver.java`
* **Cause:** annotation expressions are resolved from scheduler threads (repeating tasks, scheduled tasks) while
  the main thread adds contexts from `YamlConfig` (`addContext`). The context was a `HashMap`.
* **Fix:** a `ConcurrentHashMap`-backed `JexlContext`, and `resolve` returns `null` (instead of throwing) when
  the expression cannot be evaluated — callers already use `requireNonNull` with a helpful message.

### 6.3 `TimeUnit#toTicks` truncated and overflowed
* **Files:** `utils/TimeUnit.java`
* **Cause:** `duration.toMillis() / 50` truncates (`1 ms → 0 ticks`, i.e. "no delay"), `MICROS`/`NANOS` are 0
  milliseconds and `amount * millis` could overflow into a negative tick count.
* **Fix:** the conversion rounds **up** (`Math.ceilDiv`), clamps on overflow, never returns `0` for a non-zero
  amount and keeps the sign for negative amounts.

### 6.4 `NumberUtils` produced negative-free but wrong output
* **Files:** `number/NumberUtils.java`
* **Cause:** `abbreviateNumber` used `Math.abs(int)` — `Math.abs(Integer.MIN_VALUE)` is still negative and the
  suffix index went out of bounds; the double cast keeps `Long.MIN_VALUE` positive now. `formatNumber` built a
  `DecimalFormat` with the **default locale**, so a server running with a comma decimal separator produced
  `1,50` in messages, and the pattern had no fixed symbol set.
* **Fix:** the absolute value is computed on a `double`, the suffix is clamped, and `DecimalFormatSymbols` is
  taken from `Locale.ROOT`.

### 6.5 `ComponentUtils` had non-thread-safe registries and no `null` handling
* **Files:** `component/ComponentUtils.java`
* **Cause:** the global tag resolver list, component resolvers and modifiers were `ArrayList`/`HashMap`/
  `HashSet` — mutated at registration time and read from asynchronous tasks; `resolve(null)` threw an NPE
  instead of rendering an empty component.
* **Fix:** copy-on-write collections and a concurrent map (keeping insertion order for the modifiers), and
  `resolve(null)` returns `Component.empty()`.

## 7. Paper integration

### 7.1 The plugin lifecycle (load/enable/disable) was not safe
* **Files:** `paper/PaperWinterPlugin.java`
* **Causes and fixes:**
  * `onLoad` called `disablePlugin(this)` when the modules could not be loaded and then **continued**: it ran
    `onPluginLoad()` and logged "Plugin loaded" on a plugin that had just been disabled. Failures now abort the
    phase and are reported through one idempotent cleanup path.
  * `onEnable` shadowed the `injector` field with a local variable, so `getInjector()` only happened to work
    because Guice injects the field as a member. The field is assigned explicitly now, and the enable phase
    cannot run twice.
  * A failed load/enable disabled the plugin without releasing what had already been started (modules enabled,
    tasks scheduled, listeners registered). `shutdown()` now always runs, cancels the scheduler tasks and
    disables the modules that were really enabled, and it is idempotent so the platform's later `onDisable`
    does not clean up twice.
  * `onDisable` called `disablePlugin(this)` from inside `onDisable` when a module failed to disable
    (re-entrant disable) and called `onPluginDisable()` even when `onPluginEnable()` had never run.
  * The platform can call `onEnable` again after `onDisable` without a new `onLoad` (a `/reload` does exactly
    that). The load phase is now performed from `onEnable` when it is missing, instead of disabling the plugin.
  * `getGuiceModules()` did not bind `PluginScheduler`, `ExpressionResolver` or `PlatformPluginManager` (all
    interfaces, therefore not JIT-bindable), so any component or lifecycle method asking for them failed with a
    Guice `ConfigurationException`. They are bound to the plugin instances.
  * `namespace()` lowercased with the default locale, which can produce characters that are not valid in an
    adventure key (the Turkish dotless `i`); it now uses `Locale.ROOT`.

### 7.2 Listener components could not be unregistered cleanly
* **Files:** `paper/listener/module/ListenerModule.java`
* **Cause:** `onDisable` called `HandlerList.unregisterAll(plugin)`, which removes **every** listener of the
  plugin — including the ones the plugin registered itself, outside the framework — and `enableComponent` had no
  guard, so a second enable registered the same listener twice (every event handled twice).
* **Fix:** the module keeps the listeners it registered (keyed by component class), unregisters exactly those,
  and ignores a duplicate enable.

### 7.3 `YamlConfig` failed when there was no bundled default
* **Files:** `paper/yaml/YamlConfig.java`
* **Cause:** `load()` only created the file when a resource was bundled (`!exists && resource != null`) and then
  always called `Files.copy(input, path)`. With `resource == null` (a configuration that is created
  programmatically) the file did not exist and the read failed; with a resource that returns `null` (missing
  from the jar) the copy threw an NPE.
* **Fix:** an empty file is created when there is no default, an existing file is tolerated (concurrent
  creation) and the resource is only copied when it is actually there.

### 7.4 Generated YAML modules depended on the element order
* **Files:** `paper/yaml/processor/YamlConfigProcessor.java`
* **Cause:** the annotated fields were collected into a `Set`, and the first field that mentioned a given file
  name won the (single) binding. Which field was used — and whether `HashMap` order put a different one first —
  changed between builds. Generating twice also threw a `FilerException`.
* **Fix:** fields are sorted, insertion ordered and deduplicated per file name, and each module is generated
  once per compilation.

### 7.5 `PaperPluginScheduler` was verified, not changed
* `cancelAllTasks()` (`BukkitScheduler#cancelTasks`), `getSync()` (main-thread check + exceptional completion)
  and the tick conversions are correct; the earlier suspicion was a false positive, so the class is untouched.

## 8. Build and tests

* **Files:** `build.gradle.kts`, `core/build.gradle.kts`, `gradle/libs.versions.toml`, `core/src/test`,
  `paper/src/test`
* **Cause:** the JUnit dependencies were declared on the **root** project only, so neither `core` nor `paper` had
  a test classpath at all (the modules had no tests), `junit-platform-launcher` was missing (required by Gradle
  for JUnit 5) and the compile-only dependencies used by the tests (adventure, MiniMessage, Guava) were not on
  the test runtime classpath.
* **Fix:** the test dependencies and `useJUnitPlatform()` moved into `subprojects`, the launcher was added to the
  catalog and `core` declares the compile-only libraries it needs at test runtime.
* **Tests added** (they document the behaviour that was fixed):
  * `utils/graph/DfsGraphTest` — dependency ordering, insertion order, cycles.
  * `utils/TimeUnitTest` — tick rounding, sub-tick units, overflow clamping.
  * `number/NumberUtilsTest` — abbreviations, `Long.MIN_VALUE`, locale independent formatting.
  * `utils/reflect/ReflectionsTest` — inherited/overridden method discovery, meta annotations.
  * `utils/reflect/ProcessorUtilsTest` — `plugin.type` parsing and errors.
  * `expression/converter/ConverterRegistryTest` — super type/interface converters.
  * `expression/JexlExpressionResolverTest` — resolution, time units, converters, thread safety.
  * `service/ServiceManagerTest` — decorator discovery, handler lifecycle replay, `getOrCreateHandler`.
  * `paper/yaml/FileNameImplTest` — the annotation `equals`/`hashCode` contract used as a Guice key.

## Verification notes

The sandbox used for this review has no JDK compiler and no network access to Maven Central, so the project
could not be compiled here. Every modified file was parsed with a Java grammar (tree-sitter) to catch syntax
errors, the whole diff was reviewed by hand for API/typing mistakes, and the ordering logic of `DfsGraph` was
validated with an executable model of the algorithm. The two remaining parser complaints are a known
tree-sitter false positive on pattern-matching `switch` labels (also reported for the unmodified upstream file)
and the generated-source template, which is not a compilable Java file by design.
